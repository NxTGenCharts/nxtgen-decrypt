How this works — every leg multiplies your balance by the best bid (selling) or 1/ask (buying) available on that exchange's public order book, minus your taker fee. A positive % means the round trip A→B→C→A returns more than you started with, before slippage. All three legs of one cycle always execute on the same exchange — arbitrage never mixes order books mid-cycle. Fiat on/off-ramp pairs (USDT/TRY, USDC/IDR, etc.) and any leg under your min 24h volume are excluded before the graph is even built, the same two filters the CLI scanner applies — this is what keeps the results to cycles you could plausibly fill instead of noise from thin or non-tradeable pairs.
Theoretical (CLI-style) toggle — checking this reproduces the bundled CLI scanner's math exactly: one last-traded price for both the buy and sell leg (no bid/ask spread) and no fee subtracted. It exists so you can compare the two side by side — it is not a more accurate mode, it's the CLI's shortcut that makes its numbers look better than a real fill would be. Leave it off for a realistic read.
Live Scan — re-scans on the interval you set and tags each row NEW the first time it's seen and OPEN on every pass after that, with a first-seen timestamp — mirroring the CLI scanner's continuous-tracking output. Cycles that stop clearing the filter are logged to a closed strip above the results with how long they stayed open, then drop off.
Read before trading — this is an informational scan of top-of-book prices, not a guarantee, and it does not manufacture profit that isn't really there. Real fills depend on order book depth, execution speed, and simultaneous availability of all three legs — thin books and latency routinely erase small or negative edges either way. This is not financial advice.
Assumes pre-funded balances. This scans price gaps only — it does not model moving funds between exchanges. Real execution needs quote-asset balance already sitting on the buy exchange and the base asset already sitting on the sell exchange; an on-chain or internal transfer takes minutes, and the gap is usually gone by the time it lands.
Ticker symbols are not globally unique. This scan matches assets across exchanges by their ticker (e.g. "AI"), but the same ticker can belong to completely unrelated projects on different exchanges — there's no contract address or chain ID in these exchanges' public price data to tell them apart automatically. Known collisions are excluded from cross-exchange matching entirely rather than risk showing a fake gap between two different coins: currently AI (a different project on each exchange — e.g. Sleepless AI vs. Gensyn). They're still scanned normally within a single exchange (Triangular Arbitrage), where the ticker is unambiguous.

How this works — for every asset traded on 2+ of the selected exchanges, this finds the lowest ask (buy side) and the highest bid (sell side) and computes the spread after two taker fees. It requires the buy and sell exchange to be different — a gap on one exchange against itself isn't arbitrage.
Window, Liquidity, Transfer — Window is how long this session's scanner has continuously seen the gap ("just opened" under ~90s). Liquidity compares top-of-book depth and 24h volume on both sides against your trade amount. Transfer is anchored to Bitget's public coin/network status: if Bitget is one leg and has withdrawals or deposits disabled for that coin, it's flagged "Not transferable." Binance and Bybit don't expose network status without an authenticated account, so pairs between just those two show "Unverified" rather than a guess.
Read before trading — a live spread here is not automatically capturable — see the banner above. Transfer time, withdrawal fees/limits, and the spread closing before you move funds are the main reasons a real gap this size rarely survives long enough to execute risk-free. This is not financial advice.
Connect Exchanges
Balance verification is pre-configured for this site — nothing to set up on any device.
Your keys never leave this browser — balance verification is handled by a proxy this site already runs for you. Keys stay in this device's local storage only. Binance/Bybit's own servers reject authenticated requests made directly from a browser (that's how they prevent exactly this kind of key exposure), so this site runs a small backend (see /server in this project) that makes the one-time verify+balance check on your behalf — it never places an order or moves funds, and doesn't store the key either; see its README for what it actually does. This is pre-configured and not something you need to set up per device. Disconnecting keeps the saved key so you can reconnect later; use Remove to delete it, and the SHOW/HIDE button next to each field to reveal it.

Live vs. Demo — these are two different environments with two different sets of keys. Binance and Bybit each expose a separate Demo Trading environment (real-looking, live-mirrored prices, demo funds only — this is what the terminal bot's "Demo" auto-trade mode uses) alongside your normal Live account. A Live key will be rejected against Demo's URL and vice versa — that's the #1 cause of an unexpected 401 here. Use the Live / Demo switch on each row to pick the matching one before entering a key. Bitget has no public Demo Trading environment, so its row stays Live-only, and it can't be verified even with the proxy (its signed endpoints need a passphrase this app doesn't collect).

Scope — Autotrade only trades Triangular Arbitrage, only on Spot markets, and only on the single exchange selected above. Cross-Exchange scanning is not included. Futures trading now lives in its own AI Futures Engine tab (paper mode).
How it decides — each pass, it ranks every triangular cycle on the selected exchange and, if the single most profitable one clears both your min-profit field and the hard 0.8% floor, it "executes" it — this compounds a running day-balance rather than placing a real order (see the notice above).
Daily target — once today's simulated balance is up 11% (or your configured target) from the starting balance you entered, Autotrade stops itself automatically for the day, however many cycles it took to get there, and the summary above is the full record.
This is not financial advice, and simulated results will not exactly match a real fill — depth, slippage, and timing between the three legs all affect a real execution.
PAPER MODE only, synthetic market data. This engine is Phase 1 of the build: the scoring/regime/setup/risk/no-trade logic is real and runs every cycle, but the price data driving it is currently a seeded random-walk generator (see js/futures/mockMarket.js), not live Binance/Bybit futures feeds — that's Phase 2. Nothing here places, or is capable of placing, a real order; there is no LIVE MODE in this build. Whatever win rate / expectancy you see below is whatever the synthetic price path actually produced against these rules — it is not tuned to look good.

Scope — USDT-margined perpetuals on Binance Futures / Bybit Derivatives only, across BTC/ETH/SOL/BNB/XRP/DOGE. Default risk 0.375% of equity per trade (configurable 0.25–1%), max 3 simultaneous positions, max 1.5% total portfolio risk, max 2% daily loss, pause after 3 consecutive losses — all enforced by the No-Trade Engine before any position opens.
Win rate vs. expectancy — the dashboard reports whatever win rate and profit factor the session's trades actually produced. A high win rate with poor expectancy is not something this build is tuned toward, and it will show a losing session honestly if that's what happens against the current (synthetic) price data.
What's next — real historical backtesting, walk-forward optimization, and Monte Carlo analysis all require actual historical OHLCV + a place to store it, which this static app doesn't have yet — see the architecture notes from the initial assessment. Live order execution additionally requires server-side key storage and an execution/reconciliation service. Paper mode here is running the real decision logic today so it can be validated before either of those is built.
